Your sizes are already in your inbox

22 November 2026 · By AlephB · About What's my size?

What's my size? is a Chrome extension I am building. When you open a garment in an online shop, it looks at the shop's size chart, puts it next to the pieces in your wardrobe that you have marked as a good fit, and suggests a size. To do that it has to know what you own and the size on each label. Nobody wants to type that list in, and most people have it already, spread over years of order confirmations in their mailbox.

Below is what I learned turning those emails into a wardrobe. The extension is still in development and not on the Chrome Web Store, so I will say which parts run today and which are built but have not yet been tried on a real mailbox.

Why order emails

A Shopify app sees only its own shop's orders. Shopify's terms and data-protection law forbid pooling one customer's purchases across merchants, and no public API gives a shopper's orders across stores. A size comparison is useful because it crosses shops, so the data has to come from the shopper's side, and the confirmation email is the one place where every shop writes down what you bought and in which size.

Those emails are messy. In my first sample two Shopify shops sent clean plain text, while another retailer sent an HTML-only email whose plain-text part held nothing but stylesheet code. They also carry things a size tool has no use for: your full name, home address, phone number, the last digits of a card and tracking links.

Two ways into the mailbox

There are two versions of the reader. The first is my own prototype, which runs on my Mac. It is a Python script that uses the Gmail API to list the messages under a shopping label, strips personal details, sends the cleaned text to a cloud language model and writes the garments into a Google Sheet. It showed the idea works.

The public version cannot work that way, for reasons covered further down, so it reads Gmail the way you do. When you click "Import from Gmail", the extension opens Gmail in a background tab and searches the last two years for order and return subjects (commande, order, receipt, invoice, Bestellung, pedido, return, refund and a few more). For each hit it fetches the original message, the same raw source Gmail's "Show original" shows you. The email is cleaned in the browser and read by Chrome's built-in model, Gemini Nano, on your computer. A run sends at most 300 emails to the model and waits about a second between fetches; the next run picks up where the last one stopped. AlephB has no server, and no email text or extracted garment reaches me.

That reader is built and has its tests, but it has not yet run against a real Gmail account. The upload to the Chrome Web Store is on hold until a newer test machine arrives, so the store build can be tested there first.

Cheap filters before the model

Most emails in a shopping folder are not orders. Before any model reads anything, simple word lists drop the obvious ones: subjects about shipping or delivery, newsletters, sales, and replies to a shop thread, since a "Re:" quotes the order again. Then a size pre-filter checks that the body contains something that looks like a clothing size, either a size word (taille, size, Größe, talla, taglia, maat) followed closely by a size, or a variant line such as "M / Black".

I keep these filters loose on purpose. Excluding a real order by mistake loses a purchase for good, and letting a shipping note through costs one model call. Some junk still gets past them. A brand's monthly style newsletter once went through and was read as if the fabric mills it praised were things I had bought. I deleted that row, and I stopped expecting a word list to catch everything.

One model, then plain rules

Every shop's template differs, so I never wrote a parser per store. A language model reads each email with a strict output schema: brand, item, size as written, category from a fixed list, department, colour. The schema has no field where a name or an address could land, and that protects more than the removal of personal details, which is best effort. The prompt also says that a model name at the start of a line belongs in the item and that a marketplace seller is never the maker.

After that it is plain code, the same rules for every shop. Letter sizes are normalised (Medium and M are one size, 2XL is XXL), "EU 42" or "42 (IT)" become 42, and the usual ways of writing one-size (TU, T.U., taille unique, one size, OS, OSFA) all become TU. Waist and length have one spelling, W28 L34, whether the shop wrote 28L34, W28/L34 or 28x34. A bare "34/36" stays a span. A label that names two systems, such as 46/M, is kept whole when that is how the shop sells it.

That last rule came from a mistake. A change to the size-chart reader split every slash label into its parts, so a page selling 44/S to 50/XL counted as selling both "46" and "M", and a garment I own in 46/M found no 46 to compare with. The tests and the site runs had all passed; only a screenshot retake caught it. Since then the product pages of garments I actually own are part of the test set, because a check that only counts "chart read" misses a chart read under the wrong labels.

Two more rules came from early mistakes. When the maker cannot be known (a multi-brand shop whose email doesn't name it), the line is dropped instead of being saved under a placeholder. A garment whose email gives no size is now kept with an empty size: it shows in the wardrobe but never serves as a reference until you type the size in.

One purchase, many emails

A single order can produce an invoice, a confirmation, a shipping notice, "return requested", "return approved" and a refund email, and the return emails repeat the item and size. In my prototype's early data, several returned garments had each produced two to four extra rows from their own return correspondence. The original filter only knew "refund" and its French form, so it missed all of them.

The fix had two parts. The first reads an order number when there is one and deduplicates by order as well as by message. The number needs at least four digits, because one store's emails carried a day number that a looser pattern took for an order number. The second treats a return as a change of status: the surviving row is marked returned and never serves as a fit reference. A payment receipt, from PayPal for example, is a second copy of the order under other names and often has no order number, so a garment already bought the same day is not added again. Emails are read oldest first, so a return never arrives before its order.

Auditing the emails that gave nothing

An email that yields no garment leaves no trace in the data, so I audited those emails read-only, without printing any subject or body. Of 323 messages under my clothes labels, 153 had been read and had produced no row. The return filter had caught 30 and the shipping and marketing filter 14, as expected. The model read the other 109 again, the doubtful ones twice, for 126 calls in all. 96 still gave nothing, mostly receipts and notifications whose garments had come in through another email. The rest gave lines that the rules dropped or duplicates of rows I already had.

The audit found no rule bug. It did find one lost garment, a jacket whose email named no size, dropped by the rule that a sized garment needs a size. Such garments are now kept without a size. It also turned up a payment receipt that worded a garment's name differently from the shop's email, so deduplication now compares the set of words in a name.

Knowing which shop it came from

The store where you bought a garment is not always its brand. The sender's domain usually names the store, but many shops send through a platform under the platform's own domain. Shopify and Big Cartel shops often set their own address as the Reply-To, so my prototype falls back to that, then to a marketplace's own site, and leaves the store empty for payment receipts and mailing services. In my own data 68 garments had no store, and this filled 57 of them.

I checked four of those Reply-To guesses by hand against the shops' public pages. The store was right each time. The brand was wrong in two and probably a third: on a single-brand shop the model had taken a product's model name for the maker. A shop's public Shopify catalogue settles that without any AI, since each product lists its vendor, and my prototype now asks it. The public build does not have this lookup yet.

How Google's rules shaped the design

The Gmail API scope for reading mail, gmail.readonly, is on Google's restricted list. Using it means OAuth verification, which Google quotes at about six weeks for restricted scopes and which has to be renewed every year, and probably a yearly third-party security assessment (CASA) as well. Google's own pages disagree on whether an app that keeps everything on the device is exempt, and a developer of a local-only app reported in 2026 that Google refused it that exception. Published lab prices run from about $540 to several thousand dollars a year. The narrower gmail.metadata scope is restricted too, and it cannot read message bodies, which is where the sizes are.

So the public build never asks for a Gmail scope. It reads the Gmail tab you are already signed in to, only after a consent screen and a click from you, at a visible and throttled pace, and only order emails. Its one Google permission is drive.file, a non-sensitive scope that lets it create and use the single Sheet that holds your wardrobe. The cost is fragility, because Gmail's page structure changes without notice. The reader relies on Gmail's most stable attributes and lives in one small module with its own tests, and I expect to fix it every few months. A Google Takeout export of one label is planned as the fallback.

The model is the last open question. On my 2018 Intel laptop, Gemini Nano errored on 44 of 80 test emails, and on the emails it did answer it got 89% of items right. The old machine may be the cause, so I will judge it after a rerun on recent hardware.

Four rules for reading orders out of email

  • Never store a placeholder. Drop the record or flag it for a person, because a fake value comes back to bite you further down the pipeline.
  • Expect the filters to stay incomplete. Refunds and returns only showed up once I looked at real data. Keep the filters before the model loose and the rules after it strict.
  • Audit what produced nothing. The emails that leave no row are where a garment gets lost.
  • Check a claim against the source before writing a rule. One rule of mine filed a shop's unnamed lines as its own label, and the shop's own catalogue showed it was wrong.
