Keeping personal data on the device

22 November 2026 · By AlephB

I build small things alone: an iPhone app, a Chrome extension, a browser game and this site. Each of them handles something personal. Compromise needs everyone's starting address to find a fair place to meet. What's my size? reads order emails to learn which clothes you own. The Ritz Affair keeps your notes and SQL queries while you play. A solo developer can't run a server that holds that kind of data and sleep well, so every project started from the same rule: the data stays on the device, and I run as little backend as I can.

The rule held better in some places than in others. Below is what each project does, where a server crept in anyway, and what that cost me in features and review work, plus a few mistakes.

Compromise: addresses that never reach me

Compromise has no account. The addresses you type stay on the phone that entered them, and route questions go to Apple's maps service, which is the only place they go. The hard part was the group: if four friends want to meet, the organiser's phone needs the other three starting points.

The first answer was a link. An invite carries the organiser's first name; the friend's reply carries their way of travelling and their start, either as coordinates rounded to about five metres or as the text they typed. Everything travels after the # in the address. Browsers don't send that part to the web host, so the static page that opens the link never sees the data in it. A results link carries the chosen places and each person's minutes, and never a starting point.

A link format you can't update on a server needs strict rules, because old copies of the app will read new links for years. Mine has a version number, and a reader that meets a version it doesn't know refuses the link. Unknown fields are ignored, so I can add an optional field without breaking older apps. That rule paid off twice: the iCloud group and the reply relay below each arrived as one new optional field, with no version change. A link that fails any check is dropped entirely, and the screen says only that it can't be read.

Links alone made people copy messages back and forth, so groups now sync through iCloud sharing. Each group is one shared zone in the organiser's iCloud, with every personal field end-to-end encrypted; Apple stores ciphertext, and neither I nor the CloudKit console can read it. The storage counts against the organiser's iCloud, a few kilobytes per group, and costs me nothing. I compared this with an iMessage app, which would have left out WhatsApp users, with SharePlay, which only works during a call, and with my own server. The server would have taken two to three weeks plus running a service indefinitely, and it would have seen IP addresses and timing even with encryption.

iCloud has its own costs. A friend needs the app and iCloud to join. The App Clip can't join a share, so friends without the app still use the form and a reply link. Background updates are best effort: a phone is up to date when you open it, and you may not be pinged when something changes. Members now see each other's rounded starts, which reversed my earlier "first name only" stance. Since the group link is public, anyone it gets forwarded to can join, and nobody can be removed one at a time; the organiser has to end the group and start a new one. A group also closes itself once nobody has changed it for two days, so old zones don't pile up.

The relay I said I wouldn't build

A friend without the app still had to send a reply link back by hand. In November I gave in and built a small relay on Cloudflare for that one job, and it shipped in version 1.0.2. The invite now carries a random mailbox id and a key, both inside the #. The friend's browser or App Clip encrypts the reply with AES-GCM and posts it to the mailbox; only the organiser's phone holds the secret that reads it. A mailbox accepts twelve replies at most and is deleted seven days after it was made. The relay sees mailbox ids, message sizes, timing and the organiser's push token. It never sees names, modes or starts, and it uses IP addresses only in memory, for rate limits. If the post fails, the friend gets the old reply link.

I picked a shared key over a public-key scheme because the key-exchange curve I wanted is too recent for the browsers on the older Android phones the web reply page is there for. Anyone holding the invite could in principle read a reply caught in transit, but anyone holding it can already send a fake reply, so I accepted that.

The relay made one sentence on the app's privacy page false: "Compromise has no server". It had been true at launch. The lesson I took is to write a privacy page as a list of what goes where, so a new feature changes one line.

Counting use without following anyone

I still want to know whether people come back and where searches fail. Compromise sends its own counts to a write-only endpoint of mine: nine kinds of event, each field a number or a value from a fixed list, with no free text, names, addresses, coordinates or venue names. The one exception is a search outside every city the app covers, which sends that town's name and country and nothing finer. Each install gets a random id that is replaced after thirteen months. It lives in the app's ordinary settings storage. The Keychain survives a reinstall, which would make the id more of an identifier, so I kept it out. The IP address is never stored. Counting is on by default with a switch in Settings; turning it off deletes the waiting events and the id, then sends one anonymous "turned off" signal with no id.

The cost was the App Store privacy label. Read strictly, a persistent install id is data linked to you, so the label moved from "Data Not Collected" to "Data Linked to You", while still saying no tracking. I took the strict reading because it is the one I never have to defend. The App Clip sends nothing, because it has no off switch to offer.

I also made a mistake here. Until a build in late November, TestFlight copies reported themselves as App Store installs, so a month of daily totals counted my own test phones as App Store users, and those days' totals can't be corrected. The in-app feedback form follows the same rules as the counts: it sends the message, an email only if you type one, and app details that never include addresses, names, coordinates or places.

What's my size?: reading email without asking for Gmail

What's my size? is an extension for Chrome, not yet in the store, that compares a garment on a shop page with clothes you already own. It learns your wardrobe from order emails, which is about as personal as data gets. The store edition stores the wardrobe in a Sheet that the extension creates in your Drive; I run no server that sees it.

The obvious route was Google's read-only Gmail permission. I researched it and dropped it. That permission is on Google's restricted list even when every email is processed on the device. OAuth verification is certain, and a paid yearly security assessment is likely, because Google's own pages contradict each other on whether local-only apps are exempt. Google's policy also bars apps that export email on a one-time basis, and a one-off import of past orders could be read that way. The metadata-only permission is restricted too and can't read message bodies.

The extension asks for one permission instead: access to files it creates in Drive, which is non-sensitive and needs only brand verification. For past orders I built an import that you start yourself from your open Gmail tab, after an explicit consent screen. It reads the order emails from Gmail's own pages at a calm pace, and Chrome's built-in model extracts the garments in the browser. It hasn't been tried on a real mailbox yet. If it doesn't hold up, the planned fallback is a mailbox export you download from Google and drop on the extension's page.

Reading Gmail's pages is fragile, since its markup changes without notice, so I expect a fix every few months. The Chrome Web Store still treats email as personal communications and asks for a prominent disclosure before any email is read. The built-in model was also unreliable on my older Intel Mac: in one test it failed on 44 of 80 emails, and I haven't rerun the test on Apple Silicon.

The Ritz Affair: play without an account

The Ritz Affair is a detective game that teaches SQL, and the game runs entirely in the browser, its database too. Progress, notes and queries stay in local storage. When the game moved to this domain, the old address handed each player's saves to the new one inside the # of a redirect, so even the move went through no server.

Data leaves the browser in a few places, each optional or written down on the game's privacy page. Signing in, with Google or with an email and password, is optional and only carries learning progress between devices. The backend is a Google Apps Script writing to a Sheet. It keeps a keyed hash of your Google id and never your email or name. With a password, the browser sends only a derived verifier, so the password itself never leaves the page. A Delete button removes the saved row at once. When a teacher runs a class competition, the leaderboard receives a pseudonym and solve times. Answers are checked in the browser and never sent, and the game asks players to pick a pseudonym that isn't their full name. A feedback form sends what you type to me. The game also shows ads and loads Google Analytics, which in Europe waits for consent. The page can't see your country, so it uses your time zone as a stand-in. It's an imperfect test, and I chose it over loading anything early.

This site

The articles and other pages here set no cookies; the game and its handbook follow their own rules, above. Visits are counted with Cloudflare's cookie-free page-view analytics, and I copied its small script onto this site so the pages load nothing from elsewhere. The price is upkeep: if Cloudflare stops accepting that version, I have to copy it again. The host, GitHub Pages, still receives your IP address when it serves a page, as any web host does.

What I would keep from these four projects

  • Put data in the URL fragment. Static hosts never receive it, so it is the cheapest private channel there is and needs no server.
  • Version your formats on day one. Refuse unknown versions, ignore unknown fields, and test the reader against links from old builds.
  • Store things in the user's own iCloud, Drive or browser. It costs you nothing and keeps you out of the data.
  • Check permission tiers before writing code. On Google, the restricted tier decided the whole design of the email import.
  • Expect a server to come back anyway. When it does, encrypt end to end, give everything a short lifetime, and update the privacy page in the same release.

All four projects talk to some server, and each has a short written list of what leaves the device. Keeping that list current is part of every release.
